The Microsoft Fabric Maturity Model by Dr. Estera Kot

By Dr. Estera Kot, CTO at Clouds on Mars and former Microsoft Principal Product Manager for the Apache Spark runtime in Fabric. Published Monday, October 19, 2026.

The Fabric Maturity Model is a five-level framework for planning and measuring Microsoft Fabric adoption. Dr. Estera Kot built it on what she saw as a Microsoft product manager for the Spark runtime in Fabric. The levels are Foundation, Expansion, Integration, Optimization, and Excellence.

The model is applied in Clouds on Mars engagements. The canonical offering is the Microsoft Fabric Maturity Model in the Clouds on Mars catalog. For the step-by-step build decisions behind each level, read the Microsoft Fabric implementation guide.

Why a maturity model

Fabric spans many workloads, each with its own learning curve. Teams that switch everything on at once tend to hit the same problems. Poor engine and capacity choices drive cost overruns. Users get lost in features they did not ask for. Integration surprises appear late, and governance gaps surface only at scale.

The model replaces that with a sequence. Each level has explicit objectives and success criteria, so teams know what done looks like before they move on. The levels are stages of capability, not calendar dates.

Two principles run through every level. Start small and scale on evidence. Put governance in place before content spreads.

The five levels at a glance

Fabric Maturity Model levels with starting capacity guidance
Level Focus Exit signal Starting capacity
1. Foundation Data collection and basic reporting A governed pilot runs on schedule F2 or a Fabric trial
2. Expansion Cross-functional analytics Several departments share models F4
3. Integration A unified data platform Lineage, CI/CD, and a legacy retirement plan F8 to F16
4. Optimization AI-driven intelligence Models in production, costs reviewed F16 to F32
5. Excellence AI and real-time decisions at scale Agents and automation on governed data F64 and above

Capacity guidance is a starting point, not a rule. Size every capacity from measured use in the Fabric Capacity Metrics app. Remember the F64 line: below F64, every Power BI report viewer needs a Pro or Premium Per User license.

Level 1: Foundation

Data collection and basic reporting. This level is the proof of concept.

Objectives

  • Stand up a governed Fabric environment with a first capacity, workspaces, and an access model.
  • Prove value with one or two high-value, low-complexity use cases.
  • Train a core team on Fabric fundamentals before production work starts.
  • Build confidence in the platform with sponsors and first users.

Key capabilities

  • Ingestion from a few well-understood sources, such as SQL Server, Excel, or SharePoint.
  • A first lakehouse in OneLake, laid out in bronze, silver, and gold layers.
  • Essential Power BI reports with scheduled refresh.
  • Workspace roles, row-level security, and basic data classification with sensitivity labels.

Success criteria

  • All planned data sources are connected and load on schedule.
  • Daily report refresh runs without manual steps.
  • All target users are onboarded and trained.
  • A governance framework is documented and approved.

Technology focus

  • Lakehouse, Data Factory pipelines or Dataflow Gen2 for ingestion, and Power BI.
  • An F2 capacity or a Fabric trial, with the Capacity Metrics app installed from the start.
  • An on-premises data gateway if any source sits outside the cloud.

Challenges and how to handle them

  • Deciding the OneLake layout. Adopt the medallion pattern from day one, so later levels extend it instead of replacing it.
  • Uncertain capacity size. Start small, watch real consumption, and scale up on evidence.
  • Overengineering the setup. Keep the first environment simple. Complexity can wait for later levels.
  • Postponing governance. Set workspace rules and labels now, because rework grows with every new item.

Level 2: Expansion

Cross-functional analytics. Fabric moves beyond the pilot team.

Objectives

  • Extend Fabric to more departments and more users.
  • Integrate more data sources through automated pipelines.
  • Agree on shared data modeling standards across teams.

Key capabilities

  • Integration of multiple sources through Data Factory pipelines, Dataflow Gen2, mirroring, and OneLake shortcuts.
  • Cross-departmental dashboards built on shared semantic models.
  • Direct Lake semantic models that read Delta tables in OneLake without import.
  • Automated refresh schedules, with monitoring and alerts on failed runs.
  • Data modeling practices such as star schemas, shared dimensions, and naming conventions.

Success criteria

  • Pipelines run unattended, and failures raise alerts to a named owner.
  • Several departments use shared, endorsed semantic models instead of private copies.
  • Report adoption and data refresh time are tracked against the Level 1 baseline.

Technology focus

  • Data Factory, Spark notebooks, Power BI with Direct Lake, and Git integration for pipelines and notebooks.
  • An F4 capacity as a starting point, resized when the Capacity Metrics app shows sustained pressure.

Challenges and how to handle them

  • Pipeline sprawl. Keep pipelines simple, parameterized, and under version control.
  • Overwhelmed users. Introduce features gradually, each with training.
  • Performance surprises. Monitor capacity utilization early and tune the heaviest items first.

Level 3: Integration

A unified data platform. Analytics consolidates on OneLake.

Objectives

  • Consolidate analytics on one platform, with one copy of data in OneLake.
  • Add real-time analytics where the business needs it.
  • Industrialize data engineering with orchestration, CI/CD, and lineage.

Key capabilities

  • An enterprise data warehouse on Fabric Warehouse or on a gold-layer lakehouse.
  • Real-Time Intelligence with Eventstreams, Eventhouse and KQL databases, and Real-Time Dashboards.
  • Advanced transformations in Spark, with the Native Execution Engine turned on.
  • Automated pipeline orchestration, Git integration, and deployment pipelines across environments.
  • Fabric domains, endorsement, and lineage in the OneLake catalog.

Success criteria

  • Critical business assets have documented end-to-end lineage.
  • Code and item definitions live in Git and move from development to test to production through a defined process.
  • Legacy platforms in scope are retired or have a dated retirement plan.
  • Streaming use cases meet the latency targets agreed with the business.

Technology focus

  • Fabric Warehouse, Spark, Real-Time Intelligence, and Data Factory working on the same OneLake data.
  • F8 to F16 capacity as a starting range, with separate capacities for development and production.

Challenges and how to handle them

  • Real-time complexity. Make batch processing solid before adding streaming.
  • Migration effort. Move from Azure Synapse or other platforms in waves, with Microsoft's migration assistants where they apply.
  • Rising cost. Put cost monitoring in place before new workloads go live, not after.

Level 4: Optimization

AI-driven intelligence. The platform runs as a managed service inside the business.

Objectives

  • Put machine learning into production with repeatable operations.
  • Optimize performance and total cost of ownership.
  • Run Fabric through a Center of Excellence with clear roles.
  • Reach enterprise-grade governance and security.

Key capabilities

  • Machine learning in Fabric Data Science, with MLflow experiment tracking and model management.
  • Predictive analytics and automated anomaly detection on business data.
  • Self-service AI experiences, such as Copilot in Fabric and Power BI.
  • FinOps practices: consumption reporting by domain, showback or chargeback, and capacity right-sizing.
  • Enterprise governance with Microsoft Purview sensitivity labels, data loss prevention, and audit, plus private networking where required.

Success criteria

  • Production models are monitored and retrained through a repeatable process.
  • Cost per active user and capacity utilization are reviewed on a fixed schedule with the owning teams.
  • A Center of Excellence owns platform standards, training, and the roadmap.
  • Sensitivity labels cover the data in scope, and policies act on them.

Technology focus

  • Fabric Data Science, Copilot, Microsoft Purview, and the Fabric Capacity Metrics app.
  • F16 to F32 capacity as a starting range. Move to F64 or above when free-license report viewing matters at scale.

Challenges and how to handle them

  • AI overambition. Start with simple models and add complexity once the data supports it.
  • Governance rigidity. Balance control with agility by delegating settings to domains.
  • Technical debt. Schedule regular architecture reviews and refactoring.

Level 5: Excellence

AI and real-time decisions at scale. Data products drive daily operations.

Objectives

  • Embed AI in everyday decisions, grounded in governed data.
  • Automate actions on real-time signals, with clear human accountability.
  • Run the platform as a product with a continuous improvement pipeline.

Key capabilities

  • Fabric data agents and Fabric IQ that answer business questions from governed data products.
  • Real-time decision automation with Activator in Real-Time Intelligence.
  • Cross-cloud data federation through OneLake shortcuts and mirroring, for example from Amazon S3, Snowflake, or Azure Databricks.
  • A controlled path for preview features, tested in sandbox workspaces before production.

Success criteria

  • AI agents answer business questions from endorsed data products, with traceable sources.
  • Automated actions on live events run with named owners and human oversight where required.
  • Data products are discoverable, owned, and reused across domains.
  • New Fabric capabilities reach production through a documented evaluation path.

Technology focus

  • Fabric data agents, Copilot, Activator, shortcuts, mirroring, and the Fabric REST APIs.
  • F64 capacity and above, often split into several capacities by domain or region.

Challenges and how to handle them

  • Experimentation stalls. Create safe sandboxes so teams can test ideas without risk to production.
  • Accountability for automated decisions. Keep a person responsible for every automated action and its outcome.
  • Lock-in concerns. OneLake stores tables in the open Delta Lake format, so other engines can read the same data.

How to assess your level

Assess maturity against evidence, not intentions. The model uses a weakest-link rule. Your level is the highest level whose success criteria you meet in full, along with every level below it.

  1. Gather evidence. Pull capacity utilization from the Capacity Metrics app, the workspace and domain inventory, pipeline run history, governance documents, and report usage.
  2. Score seven dimensions. Rate each one against the success criteria of every level. The dimensions are strategy and sponsorship, data integration, architecture and engineering, analytics and AI, governance and security, operations and cost, and people and adoption.
  3. Apply the weakest-link rule. Take the lowest dimension score as your overall level. A strong architecture does not make up for missing governance.
  4. Plan the next level. Turn each unmet criterion for the next level into a backlog item with an owner and a date.
  5. Reassess on a fixed rhythm. Repeat the assessment every quarter and after major changes, such as a migration wave.

Quick diagnostic questions

Foundation
Does a Fabric capacity have a named owner? Are workspace roles assigned to groups, not individuals? Does at least one report refresh on schedule from Fabric data?
Expansion
Do pipelines run unattended, with alerts on failure? Do several departments use shared, endorsed semantic models?
Integration
Are code and item definitions in Git, with promotion through environments? Do critical assets have end-to-end lineage? Is there a dated plan to retire legacy platforms in scope?
Optimization
Are machine learning models monitored and retrained through a repeatable process? Is consumption reported per domain? Does a Center of Excellence own standards and training?
Excellence
Do AI agents answer business questions from governed data products? Does every automated action on live events have a named, accountable owner?

How Clouds on Mars applies the model

Clouds on Mars applies the Fabric Maturity Model in its Fabric engagements. The offering is listed in the Clouds on Mars catalog as the Microsoft Fabric Maturity Model. Its initial phases are scoped at 4 to 16 weeks, depending on the data estate, and follow four steps.

  1. Assessment and planning. Current-state architecture review, stakeholder alignment, and a technical readiness check. The deliverable is an implementation blueprint and project charter.
  2. Foundation setup. Workspace configuration and governance, the security framework, data source connectivity, and first user training. The deliverable is an operational Fabric environment.
  3. Iterative development. Reports, dashboards, and analytics built in short cycles with user feedback. The deliverable is a set of production-ready analytics solutions.
  4. Scale and optimize. Capacity tuning, advanced features such as AI and machine learning, and adoption support. The deliverable is a scalable enterprise platform.

Each engagement sets up a Fabric Center of Excellence with defined roles. It also sets a success metrics framework: cost per active user, data refresh time, report adoption, and time to insight.

Four factors decide success at every level: executive sponsorship, a cross-functional team, structured training, and an iterative approach with regular feedback.
